Executive Summary

Overall Verdict: Pre-Launch Stage (45/100 ▲ from 38 after 18 fixes)

This application has a functional core ordering flow but is NOT ready for production use with paying customers. The product suffers from 2 critical security vulnerabilities that expose customer data to any attacker, zero billing infrastructure (the subscription settings are non-functional UI mockups), 14+ business logic defects causing data corruption and revenue leakage, and 12 scalability blockers that will crash under load.

1. Security Analysis

File: main/sujay/api.php  |  Type: Missing Authentication

Added DB-based authentication. A sujay_api_users table stores hashed credentials. Every request must pass sujay_user and sujay_pass parameters. Default credentials: username sujay, password sujay123 (hashed with password_hash()). OpenRouter API key also moved to env() with fallback.

✓ Fixed July 2026 — sujay/api.php now authenticates every request against DB. Create more users by INSERTing into sujay_api_users table.

C2: Hardcoded Production Database Credentials RESOLVED

File: main/db_connection.php  |  Type: Secret in Source Code

Production credentials (u509616587_restrogrow / Sujaysarraf@5569) were hardcoded in PHP. The existing env_loader.php was not used for DB credentials. Had been committed to git history.

Impact: Any directory traversal, compromised dev machine, or .git exposure would give full database access. All tenant data compromised.

✓ Fixed July 2026 — db_connection.php now includes env_loader.php and reads DB_HOST_LOCAL, DB_NAME, DB_USER, DB_PASS from environment variables via the env() function. Production credentials removed from source code. Revoke old password and update .env file.

Added PhonePe X-VERIFY header checksum verification to both payment_link_callback.php and phonepe_callback.php. ✓ Fixed July 2026 — X-VERIFY validation added to both callbacks. PhonePe auto-confirm via redirect URL removed from order payment flow.

Files: superadmin/api.php, admin/auto_login.php  |  Type: Token Leakage

Auto-login token is now stored in PHP session instead of URL. Token never appears in server logs, browser history, or referrer headers. Already had 5-min expiry and single-use (cleared from DB after first consumption).

✓ Fixed July 2026 — superadmin/api.php stores token in $_SESSION, auto_login.php reads from session. No URL params needed.

Category SEO Score: 15 / 100

Restaurant menu pages have near-zero SEO optimization. Categories are loaded client-side via JavaScript with no individual URLs, no meta tags, no structured data, and no sitemap entries. The main marketing site (restrogrow.com) has proper SEO with canonical URLs, OG tags, and schema.org structured data, but the individual restaurant menu pages that customers actually browse are invisible to search engines beyond the homepage title tag.

Positive: The main site landing page (index.html) has excellent SEO foundations — canonical URL, OG tags, Twitter cards, 4 types of schema.org structured data (Organization, SoftwareApplication, LocalBusiness, BreadcrumbList), and a sitemap.xml. Restaurant-level menu pages have basic title tags and PWA manifest links.

Negative: 12 SEO gaps on customer-facing restaurant pages. No meta descriptions. No OG/Twitter tags for social sharing. No canonical URLs (duplicate content via restaurant_id vs slug). No schema.org markup for MenuItem or MenuSection. No BreadcrumbList structured data despite a visual breadcrumb existing. Categories are rendered via JS with no SSR fallback. No SEO fields in the database (can't set per-category title/description). No hreflang tags despite multi-language support. Above all, no individual category URLs — all menu categories load on a single page via JS, making them uncrawlable by search engines.

High Severity Gaps

1
No individual category URLsHIGH

All menu categories (Starters, Main Course, Beverages, etc.) load dynamically on a single menu.php page via JavaScript. Search engines cannot index individual categories. No URL structure like /menu/starters or ?category=starters exists. This is the single biggest SEO blocker — 100% of category-level content is invisible to Google.

2
No meta description or OG tags on menu pagesHIGH

menu.php and index.php lack <meta name="description">, <meta property="og:title">, <meta property="og:description">, <meta property="og:image">, and Twitter card tags. Social shares show bare URLs with no preview. Search results display generic snippets instead of compelling descriptions.

Medium Severity Gaps

3
No canonical URLs on restaurant pagesMED

Restaurant menus are accessible via ?restaurant_id=X AND ?restaurant=slug. No <link rel="canonical"> is set — Google sees duplicate content. Slug-based URLs should be canonical to avoid split ranking signals.

4
No MenuItem / MenuSection schema.org markupMED

Despite having detailed menu item data (prices, descriptions, dietary types, images, availability), there is zero schema.org structured data for MenuItem, MenuSection, or Restaurant. Google cannot display rich results (price, availability, rating stars) in search snippets.

5
No BreadcrumbList structured dataMED

A visual breadcrumb exists (.category-breadcrumb in menu.php) showing the current category, but there is no JSON-LD BreadcrumbList schema.org markup. Search engines can't use breadcrumb trail in SERP snippets.

6

The `menu` and `subcategories` tables have no columns for seo_title, seo_description, seo_keywords, or og_image. Restaurant owners cannot optimize individual categories for search. This requires a database migration to add columns plus admin UI fields.

7

Multi-language support exists via translate_utils.php and menu items have translations stored in JSON. However, no hreflang link tags are generated for different language versions. International search engines can't serve the correct language variant.

8

The sitemap.xml only covers the main marketing pages. Individual restaurant menus and categories are not included. A dynamic sitemap.php should be generated listing all active restaurant menu URLs with category filters.

9

Menu items and categories are loaded via fetch() API calls and rendered client-side with innerHTML. While Google can execute JavaScript, it's not guaranteed — especially for deep-linked content. SSR (server-side rendering) for initial category HTML would ensure crawlability.
